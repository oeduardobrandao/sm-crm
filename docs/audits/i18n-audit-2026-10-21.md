> Status: defect 1 and defect 4 (`<html lang>` part) plus the Vitest guard ship in the PR that adds this report. The guard also caught 3 missing Hub keys (`nav.openMenu`, `nav.menu`, `hub.clientPortal`), fixed there too.
>
> Follow-up PR: `getIntlLocale`/`useDateFnsLocale` helpers in `@mesaas/i18n`; `components/ui` dialog confirm-close and date/month pickers translated; dates follow the language in modules whose copy is already translated. Untranslated modules deliberately keep pt-BR formatting until their own migration (switching only the date would produce "21 de October" under Portuguese labels). Scope: `apps/crm/src` against `packages/i18n` (pt, en). Static analysis plus reading the

## Headline

Switching to English translates a thin shell, not the app. **83 of 576** CRM `.tsx` files
use i18n at all. The sidebar, mobile nav, login/auth, dashboard, clients list, leads,
automations and parts of client detail translate. Everything else renders Portuguese in
English mode.

## What already works (don't "fix")

- **pt/en key parity is 100%** across all 19 locale files. No missing, extra or empty EN keys.
  Identical pt/en values are brand names, `Status`, `Feed`/`Reels`/`Stories`: correct.
- All 8 CRM namespaces are registered in `main.tsx`. The `hub*` files belong to the Hub and
  are correctly not loaded by the CRM.
- All 33 sidebar `labelKey`s in `nav-data.ts` resolve in both languages.
- The imperative Instagram/TikTok HTML renderers re-run on `i18n.language` and pick
  `en-US`/`pt-BR` formatting from it.
- `fallbackLng: 'pt'` + `fallbackNS: 'common'`: a missing EN key degrades to Portuguese
  text, never to a raw key.
- The switcher (`Sidebar.tsx` → `changeLanguage`) persists to `localStorage['mesaas-language']`
  and re-renders `useTranslation` consumers live.

## Defects

### 1. Keys used in code that exist in neither locale (8)

Each call passes a Portuguese default, so English mode shows the Portuguese default.

| File                                        | Key                                                                  |
| ------------------------------------------- | -------------------------------------------------------------------- |
| `components/layout/GlobalSearchDialog.tsx`  | `topbar.searchPlaceholder`, `topbar.noResults`                       |
| `components/layout/GlobalSearchTrigger.tsx` | `topbar.search`                                                      |
| `pages/clientes/ClientesPage.tsx`           | `clients:table.client`, `table.contact`, `table.status`, `emptyList` |
| `pages/clientes/phone/ClientesPhone.tsx`    | `clients:emptyList`                                                  |

Also in global search: results render `item.label` (the raw PT nav label) instead of
`t(item.labelKey, item.label)` as the sidebar does (`GlobalSearchDialog.tsx:305`).

### 2. Dates, numbers and weekday/month names stay Brazilian

- 46 files import date-fns `ptBR` unconditionally (40 of them have no i18n wiring at all).
- 156 hardcoded `'pt-BR'` in `Intl.*` / `toLocale*` calls.
- No `dayjs.locale` wiring.
- Only the Instagram/TikTok cards and `LatestInstagramPosts` derive locale from `i18n.language`.

Fix shape: one `useDateLocale()` / `getIntlLocale()` helper in `@mesaas/i18n` that maps
`i18n.language` to `ptBR`/`enUS` and `pt-BR`/`en-US`, then replace call sites. Currency
stays `BRL` (business fact, not UI language); only its number formatting should follow the
locale.

### 3. Shared primitives leak Portuguese into every page

`components/ui/` was hand-localized to Portuguese and has no i18n:

- `dialog.tsx`: `CONFIRM_CLOSE_MSG`/`TITLE`/`DISCARD`, close-button `aria-label="Fechar"`
- `date-picker.tsx`, `date-range-picker.tsx`, `date-time-picker.tsx`, `month-picker.tsx`:
  default placeholders ("Selecionar data", "Horário:", "Mínimo N min no futuro")
- `month-grid.tsx`: `WEEK_DAYS = ['Seg', …]`, "Mês anterior" / "Próximo mês"

`common.json` already has `weekdaysShort` and `months`, so these are cheap wins with wide reach.

### 4. `<html lang>` and page titles never change

`apps/crm/index.html` ships `<html lang="pt-BR">` and nothing listens to `languageChanged`,
so screen readers and browser translate prompts treat the English UI as Portuguese.
Add `i18n.on('languageChanged', l => document.documentElement.lang = l === 'en' ? 'en' : 'pt-BR')`
in `initI18n` (and set it once at init). 11 `document.title =` assignments are PT literals.

### 5. Service/store error messages are Portuguese literals

`services/*`, `store/*`, `lib/notification-catalog.ts`, `lib/notification-config.ts` throw or
return PT strings that surface in toasts. These need `i18n.t` at the call site where they
are shown, not at module load (module-level `i18n.t` would freeze the language at boot).

## Guardrails (none exist today)

No test checks locale parity or that `t('...')` keys resolve, and ESLint has no i18n rule.

1. **Vitest guard** (cheap, would have caught defect 1): flatten pt/en, assert equal key sets;
   scan `apps/crm/src` for literal `t('…')`/`i18n.t('…', { ns })` and assert each resolves in
   its namespace or `common`.
2. **`eslint-plugin-i18next` `no-literal-string`**, enabled per directory as each module is
   migrated, so coverage ratchets instead of regressing.

## Suggested order

1. Defects 1 + 4 + guard test (one small PR).
2. Defects 2 + 3: locale helper and `components/ui` (one PR, touches every page visually).
3. Module migrations, one PR each, biggest user-facing first: Entregas, Calendário,
   Configuração, Tarefas, client detail remainder, Mensagens, Arquivos, Financeiro, Equipe,
   Analytics trio, Relatórios, Ideias, Importar, Ajuda/Guia, Afiliados. Turn the ESLint rule
   on for each directory as it lands.
4. Decide policy for public/legal pages.
